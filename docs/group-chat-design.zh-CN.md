# Agent Frontdesk 群聊设计评审

## 跨 Agent 选人与专用会话

建群时可以跨 Agent 混选已有会话，也可以添加由支持创建的 Agent 担任的专用成员。专用成员第一次收到发给它的任务时，Frontdesk 才通过原生桌面通道为它开会话。首次投递与会话绑定保存在群记录里。服务重启后继续核对同一次创建。原生会话绑定后，群成员头像可跳回该会话，后续消息继续发到同一个会话。

## 原始设计提案

设计提案，基于本地提交 `36c3666`。以下行为和验收值均为设计目标。本轮只核对了源码，没有创建测试群或执行桌面派发。

## 用户看到的群

对日常总控说「把 A、B、C 拉个群讨论实验」。总控用已有的协作关系或轻量检索解析成员。有重名才显示候选。群创建成功时，有一个稳定入口、三个原会话引用，以及一个新建并验证过的原生群主会话。初始上下文只有议题、成员及有来源的一句话职责；职责不清就保留未知。建群本身不会给成员发送欢迎词。

总控侧栏中「群聊」与「协作会话」并列。点群名进入讨论，点头像回到原会话。默认只列置顶、待你处理和最近的群，其余按需搜索或分页。恢复日常总控时只读取这一页目录；历史群的数量不决定模型提示的长度。

| 在群里做什么 | 交给谁 | 收到回复后 |
|---|---|---|
| 直接选中成员 B，发送「这个结果用了哪个测试集？」 | 只发给 B。收件人绑定具体会话，发送前可见。选了「引用」才附上那条群消息 | 答案入群，本次请求结束 |
| 说「让 A 先说结果，看是否需要 B 复核」 | 群主向 A 提问并登记答完后需要判断 | A 的答复入群。群主取本轮相关材料，决定追问 B、总结或请用户澄清 |
| 说「依次问 A、B 同一个问题」 | 群主可预先给出两个明确动作。服务按顺序派发 | 若用户只要收集答案，到齐即止；若要求比较，再唤起群主一次 |
| 在总控问「昨天实验群最后选了哪个基线？」 | 总控按主题、别名、时间查目录，再取命中群的有出处决定 | 能从记录回答就返回原话链接；两个群都匹配就列候选 |
| 请求「把结论汇报给总控」 | 向指定日常总控发一条摘要和群入口 | 同一次汇报只产生一条回执。微信外发另按原请求和绑定核对 |

普通文本里的“@B”、引用里的命令、日志和模型回复均作为内容显示。只有用户在成员选择器中确认的收件人，或本轮主持协议明确给出的成员动作，才触发派发。群消息展示作者与实际发送角色。成员桌面仍会看到走本机通道的用户消息，正文带群和发起来源；审批在对应原生会话中处理。

## 用反例检验几个候选方案

| 初始想法 | 足以推翻它的情况 | 调整后的选择 |
|---|---|---|
| 所有群共用一个总控会话，用群名区分 | 两个同名实验同时进行；旧群回执在新群指令之后到达。即使路由正确，每个回执仍会占日常总控上下文 | 群有稳定 ID 和专属群主绑定；回执先入群。日常总控只在用户请求时收到有关材料 |
| 所有成员广播，每次由模型挑下一位 | A 给出长报告，B 只需复核其中一个数字，C 只是旁听。全员订阅后，第二轮又会带上第一轮的复制内容 | 页面展示群内全部发言；模型只收到自己的任务、必要引用和继续工作的依据 |
| 建一个群就常驻一个群主进程并轮询全员 | 有一百个群，今天只有两个活跃；重新打开侧栏就可能让所有桌面忙于读取历史 | 建群时绑定原生会话；后台只调度待投递、待回执和待决策的工作。空闲群没有专属定时器 |
| 把所有群主放在日常总控目录，直接复用它的命令工具 | 现有工具按引擎和目录内的连接文件识别日常总控；同一目录中的不同聊天不能凭这个文件证明自己属于某个群 | 群主使用独立于日常总控的已登记项目。首版由服务识别自己发给群主的原生轮次，并校验该轮有限的主持动作，群主不需要日常总控的通用派发凭据 |
| 把群主原生聊天直接当成群历史 | 用户直接 @B 三次，本来无需唤起群主；要让它的聊天“完整”，只能把三问三答再复制进去 | Frontdesk 维护群消息索引和已公开的必要摘录。群主保留主持历史，需要判断时才读取相关增量 |

对这个方案本身也有一个重要反例：如果用户平时大部分时候只是 @ 一个成员，一套自由讨论引擎会给每次提问增加延迟和费用。直接 @ 是独立的短路径。已有群主不会因为用户打开群或成员提交普通回复而自动运行。试用时如果用户很少需要主持，后续优先完善群检索和引用，暂缓扩充自动讨论。

还有两笔无法由路由优化消除的成本。按用户指定的方式，创建一百个群最终要创建一百个原生群主会话，桌面项目列表会增长，部分引擎的初始化首轮还会消耗额度。因此建立一个独立的群主项目，把群集中在那里；临时对某个会话问一次仍可使用原有协作入口。建群时清楚显示会新增哪个引擎的会话，失败重试沿用同一个创建请求。每群分配独立工作目录虽便于整理产物，在 Codex 上却可能带来重复添加项目、同名项目误选和大量桌面项目，故不作为默认布局。

另一笔成本是语义判断。若每个回答都可能改变下一位发言人，群主就要在每个分支判断时运行一次。对提前指定顺序的问题可完全由服务推进；对「问到原因清楚为止」，建议原型采用每次用户请求最多三次自主成员派发的可见默认值。预算按请求持久化，重启或重复回执不能将它清零。到限后展示已知结论和未决点，由用户决定是否继续。该数值是待试用验证的假设。

## 总控的记忆归属

- **目录归当前 Frontdesk 配置。** 用稳定的目录所有者标识关联群，将创建者原生会话 ID 留作来源。日常总控换了原生会话，仍能找回自己管理的群。不同配置的同名群各自独立；切换总控引擎也不会悄悄接管别人的群。
- **正文归各自的桌面，群内公开记录归群。** 群内发言保存当时实际发布的短文或必要摘录，并指向原生引擎、会话、轮次及消息。长报告默认保存引用；按需展开。源会话归档、删除或附件失效时，已发布摘录标明来源状态，界面不会从相似会话补写原文。归档群会停止新的派发，保留已有发言和待核实回执。
- **决定要有出处。** 用户固定的结论和群主提出的暂定结论分开标注，都链接到依据。后来的决定可以取代旧决定，并保留变更顺序。首版先按群名、别名、主题、成员和最近活动检索。检索失败时显示候选或请用户补充线索。只有实际用例表明这些字段不够，再考虑语义索引。
- **主持记忆有读取进度。** 每次判断携带当前问题、被回复的发言、仍有效的决定和有界的增量。长时间离开后，群主先看未决事项和引用索引，按需展开原话。记录「已处理到第几条」与用户已读位置相互独立。过期判断返回时，服务先检查相应请求是否已被用户取消或改写，再决定是否继续。
- **同一原生会话跨群复用有真实代价。** B 在两个群里仍是同一个 B，会记住它在两边亲自参与的工作；即使路由完全正确，模型也可能在回答时提到另一边。成员详情显示其复用情况，添加时可见。若话题需要隔离，就选择单独的原生会话，必要时再隔离工作目录与资料访问。群 ID 只解决路由，不能提供桌面进程的安全隔离。

## 创建、投递和恢复

群 ID、群主绑定、群成员、群发言、投递和决定是需要持久化的最小关系。发言有群内顺序和「回复哪一条」，投递有稳定的投递 ID、目标引擎及会话、所属请求、原生轮次、下一步和确认状态。建议在当前配置内使用 SQLite 做这些新增记录与索引，沿用原有单实例所有权；每群一个数据库、定时器或宿主进程都不必要。日常总控旧 JSON 和微信绑定先保持兼容。

1. **建群。** 用户明确说建群时才新建群主。先保存创建请求 ID 和成员快照，再通过桌面创建原生聊天。Codex 优先复用单独登记的群主项目，在其中创建不同原生会话；Antigravity 可指定工作目录。用唯一初始化标记、引擎和目录共同核对，并约束一个原生群主只能绑定一个群。没有唯一匹配就显示「正在确认群主」并保留原请求。候选仅剩一个也可能是用户刚刚手动开的聊天。群主失效后仍可查看群记录，重绑或更换群主由用户决定，并留下换届记录。
2. **派发。** 一个事务内记录群消息和投递意图，再由服务走现有 RunService 及插件发送。按目标原生会话串行仲裁，涵盖多个群和普通网页发来的消息；正在执行的直接工作优先完成。首版群任务默认排队，避免两个群挤进同一原生轮。用户从桌面手动发言仍由桌面决定，Frontdesk 只认自己那条投递的证据。普通网页消息也能看到目标会话有待办，群任务等待可取消。
3. **接收。** 区分「已登记」「已在原生记录中看到」「正在等你」「有原生结束证据」「投递待核实」。成员回复按投递标记及原生轮次关联，只发布属于本群的发言。网络中断、应用关闭或标记缺失都不能证明发送失败。重启先查询原生证据；无法确定时保留待核实，可查目标原话。端到端不承诺绝对只送一次，但服务必须能去重已知回执，并禁止自动重发证据不明的请求。
4. **继续主持。** 每个待办写明答完是直接入群结束，还是交给群主判断。只有从该群当前主持请求得到的结构化结果，才能提出「问指定成员」「总结」「等用户」等有限动作。服务校验群、成员、来源轮次、请求版本及剩余轮数；无效结果保留为普通发言。成员给出的文字不会直接变成派发命令。设有界的自动轮数，用户可显式继续；「暂停本次讨论」阻止后续自动派发。中止成员已经运行的原生任务是独立操作，须能确认归属。
5. **恢复和变更。** 按未完成投递恢复监听，按目标合并读取，离线时退避。移出成员会取消尚未发送给它的工作；已经发送的任务仍按原投递归属核对结果，并禁止从旧回执开启下一轮。迟到结果保留原提问的链接。无法再打开的成员标为不可用。归档群不会删除成员会话或群主原生历史。

主持动作的具体桌面载体要在原型中决定。优先验证能否从已匹配轮次的最终回复中稳定分离自然语言和结构化动作；输出格式失效时停在待处理。若改用本地工具，需要按群、按本次主持请求授予能力。多个群共享目录不能作为授权判断，普通编码代理自身能读哪些文件仍取决于其桌面权限。

## 对其他模块和用户习惯的影响

| 模块 | 短期改动 | 若长期放任，会发生什么 | 处理方式 |
|---|---|---|---|
| 侧栏、草稿、后退和未读 | 群成为可独立打开的页面 | 用户切群后把草稿发到另一群；同一回答在成员、群和总控重复提醒 | 群路由和草稿以群 ID 为键，收件人随草稿恢复；从群跳成员再返回保留位置。群未读按发言计算，日常总控不累计成员回复 |
| 运行、队列和审批 | 群向已有会话发送工作 | 热门成员成为瓶颈；用户误以为「群里等回复」等于「成员卡死」 | 显示排队、运行、等审批及待核实；带来源进入原会话处理审批。首版不增加第二套桌面审批或执行器 |
| 微信和通知 | 用户可能从微信发起一次群工作 | 若把微信来源继承给所有子任务，讨论碎片可能进入私聊；手动换绑后还会错发 | 群内投递完成默认只入群。明确请求的报告绑定一次性回报目的，发送前重新核对当前绑定；绑定改变就保留报告供查看 |
| 引用、文件和搜索 | 群发言可以引用某次原生回复 | 整段私聊、绝对路径或不断嵌套的摘要可能被带入无关会话；群主也可能重复搜索到自己 | 默认引用选中的发言，显示将实际发送的摘录。群主和日常总控从普通成员候选中排除；群内不自动同步文件或整个仓库 |
| 多插件与维护 | Codex、Antigravity 可候选群主，DSH、Claude 等可作成员 | 每加一种 agent 就复制一份群路由和回执逻辑，升级桌面后很难查出是哪一层出错 | 插件只声明创建、定位、投递和原生证据能力。群策略留在服务端；网页、主控工具使用同一组操作。能力不足时显示具体卡点 |

## 首版与放行条件

先用两个真实群共用一个测试成员，验证「建群、直接 @、原生回执、重启恢复」。这一步已经能交付多人协作入口。再加入「问 A、判断、问 B、总结」的有限主持循环，最后接显式回报。旧的单会话协作继续走原有流程；先为两种流程建立行为测试，再提取共享投递逻辑。首版的决策中不需要语义向量库、全员广播、嵌套群或自动群间转发。

| 必测场景 | 通过标准 |
|---|---|
| 100 个空闲群，打开侧栏；再模拟每群各收到一条已关联的普通回执 | 日常总控新增轮次为零；空闲群没有专属监听或对桌面目录、正文的群功能读取。明确区分普通活动栏已有的后台读取，并分别计数 |
| A、B、C 入群，只直接 @B | 只有 B 收到一次任务；群主和日常总控均无新增轮次。点引用回到 B 的准确原文 |
| 两个群同时 @B，期间用户从桌面与 B 私聊 | 两群各自显示对应轮次；私聊内容不入群。无可靠关联时进入待核实；不拿最新一条回复猜测 |
| 两个同名群并发创建，期间桌面另开一个聊天 | 各自通过唯一标记与目录绑定原生群主；不确定的候选保持待确认。刷新、切换引擎、服务重启后仍恢复原群 |
| 分别在投递前、桌面收到后、写回执前终止服务；重复注入回执 | 已确认回执只发布一次；可核对的继续，不明确的留待核实；取消、归档后没有新的自动派发 |
| 群主离线、成员待审批、成员退出、微信在任务途中换绑 | 界面能指出正在等谁；群历史仍可查看；回执来源可查；不向新绑定私聊发送旧报告 |
| 替换日常总控原生会话，再问一条已被推翻的旧决定 | 仍能检索群，展示最新决定、取代关系和原始依据。查一个群产生的正文读取与其他群数量无关 |

若 Codex 实机不能唯一绑定群主，就保留待确认状态，并先开放已验证的宿主。若某插件不能把工作可靠关联到原生轮次，就不开放该插件的自动继续。若两群并发测试出现一次跨群回执，暂停发布自动主持，先修复归属。试用期间分别计数目录检索、正文读取、模型唤起、重复投递、待核实次数和排队时长，才能判断复杂度究竟花在哪里。
